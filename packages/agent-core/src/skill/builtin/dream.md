# /dream — 让记忆沉淀成规则

记忆系统会随时把做完的事记成结构化条目。它们详细，但散。这个命令做的是**整理与升级**：把重复的合并，把模糊的提炼成一句规则，把反复出现的同类问题上升成一条规律。

**判定标准不是「记忆变少」，而是「下次能用得上」。**

## 三种动作，缺一不可

| 动作 | 什么时候用 | 结果 | 源记忆 |
|---|---|---|---|
| **合并** | 几条记忆其实是同一件事记了多遍 | 一条更完整的新记忆 | 被替换（可撤销） |
| **提炼** | 一条记忆讲清了，但没有一句话结论 | 同一条记忆多一句规则 | **保留** |
| **归纳** | 几条记忆同主题但不是重复，背后像有同一条规律 | **新增**一条规则记忆 | **全部保留** |

**没有「删除」这个动作。** 记忆不会因为「任务早就完成了」而被清掉——完成是记忆的正常状态，不是该消灭它的理由。

## 规则要写成什么样

一句能直接照做的事，不是事件复述：

- ✅ `当 npm 刚发布就安装报 404 时，先等两分钟再重试，不要立刻怀疑包坏了。`
- ✅ `When a lockfile change is the only diff, run the frozen install first.`
- ❌ `这次部署遇到了 404，等了等就好了。`（复述事件）
- ❌ `合并 3 条相关记录。最新方案: 等待。`（包装话术，工具会拒收）

要求：≤ 200 字，含**触发条件**或**明确动作**；不满足就跳过这条。

## 步骤

1. **`MemoryConsolidatePlan`** — 一次不传参的调用，返回四类材料：
   - `duplicateGroups`：相似度已达合并门槛的组，每组带一个草稿（`merged.distilled` 是空的，等写）
   - `nearMisses`：接近但没到门槛的配对，供你判断要不要合并
   - `distillCandidates`：值得提炼成规则的单条记忆
   - `inductionClusters`：共享同一主题的记忆，可能藏着一条规律

   如果它回答「nothing new to integrate」——**这就是完整结果**，如实告诉用户「这次没有需要整理的」，结束。不要为了做点什么而硬凑。

2. **写规则** — 逐类处理：
   - 合并：为每组写一条真正的 `distilled`，并把 `merged` 的其余字段润色成一条自然、完整的记忆；
   - 提炼：为候选写 `distilled`，`approach` 可顺带润色；
   - 归纳：若一组里确实存在一条能覆盖全组的规律，就写 `rule`；**看不出来就跳过**——归纳是发现规律，不是每簇都必须产出一条。

3. **先确认，再落盘 `MemoryConsolidateApply`** — 用 `AskUserQuestion` 把将要发生的改动摆给用户（合并哪几组、为哪几条补规则、新归纳出什么），得到同意再执行。入参只有 id 和你要写入的文本：
   ```json
   {
     "merges": [{ "memoIds": ["…"], "merged": { "…": "…", "distilled": "…" } }],
     "distillations": [{ "memoId": "…", "distilled": "…" }],
     "inductions": [{ "topic": "…", "sourceMemoIds": ["…"], "rule": { "…": "…" } }]
   }
   ```
   工具会逐条校验：id 不存在、规则不像规则、想覆盖已有规则却没 `allowSupersede` —— 这些条目进 `skipped` 并说明原因，**不影响其它条目**。读到 `skipped` 就修正后重试那一条。

4. **如实汇报** — 用用户的语言说清三件事：合并了几组、为几条记忆补了规则、新归纳了几条规律；有 `skipped` 就说明卡在哪。合并给过 `merge id`，一并告诉用户，他们可以撤销。

## 几条硬规矩

- **一次只处理计划给的范围**：它是增量的，剩下的下次再来，别自己扩大范围。
- **不碰已经带规则的记忆**：那是精炼过的结果。确实要覆盖，必须显式 `allowSupersede`，并先告诉用户。
- **合并前想清楚**：合并会替换源记忆。两条记忆只要还带着不同的信息，就不该合并——合并的目标是更完整，不是更少。
- **不编造**：规则只能来自记忆里已有的事实。记忆没说的，不要补。
