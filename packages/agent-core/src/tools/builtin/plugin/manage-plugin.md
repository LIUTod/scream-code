Manage this product's own plugins — the vehicle for add-on capabilities: a plugin can contribute skills, MCP servers, shell hooks, and (only after an explicit `activate`) code that runs in this process.

Use it when a task needs a capability you do not have (exhaust your existing tools first, and remove or disable the addition when the work is done unless it is broadly reusable), or when the user asks you to find, install, configure, inspect, or clean up a capability. For "what can you do" questions answer with **InspectOwnAssets** instead — `{"action":"list"}` here is the plugin-management view, a pre-change check of the plugin table. Prefer the lightest vehicle: a skill (prompt only), then an MCP server (external process), then a code plugin (needs an approved `activate`).

Actions: `list`; `marketplace` / `precheck` (browse the catalog / free read-only origin check reporting incidents from the plugin center's immune memory, `quarantined:true` plus the reason — run it before installing anything you have not vetted this session, and surface such a warning to the user BEFORE asking for the install approval); `install` (local path, GitHub URL, or zip URL — **installing never executes code**; `upgrade:true` backs up the current files first); `register_generated` (register a directory you built — it refuses any manifest declaring an `entryPoint`, since it is normally auto-approved and must never become a route to running code); `enable` / `disable` / `set_mcp_enabled`; `activate` / `deactivate` (the only actions that run a plugin's code entry point — skip for skill-only and MCP-only plugins); `info` / `check` (one record / table health); `reset` (recover a tripped or disabled plugin — clears the failure ledger, re-derives from disk, enables and hot-applies, never runs code); `rollback`; `reload`; `remove`. `id` is required by info, enable, disable, set_mcp_enabled, activate, deactivate, remove, reset and rollback.

Approval contract: read-only actions (`list`, `info`, `check`, `marketplace`, `precheck`) run without prompting; every mutating action requires the user's approval — state what you are about to do in one line, then call it. The prompt shows the full source string for `install`/`register_generated`, and a session grant covers that exact source only. `activate` executes third-party code and is its own decision. A rejected approval is an answer, not a retry cue.

Circuit breaker: every failed plugin-owned call and faulty event handler counts against its plugin; three consecutive failures trip it — the plugin is marked with the reason, disabled persistently, its code deactivated, and its tools/MCP servers/skills/hooks pulled from live sessions, with a `[circuit]` advisory on the failing result. Nothing retries automatically: read `circuit:{failures, tripped}` with `check`, then `reset` or `remove`. A trip is also written into the quarantine ledger, so later `precheck`/`install`/`marketplace` calls for the same repository surface that history even across sessions.

Mutating actions hot-apply where the host supports it and report `sync:{ok, applied[], failed[]}` naming what landed (`skills.inject`, `mcp.add`/`mcp.remove`, tool teardown); `install` reports no `mcp.add`, because installing never starts a plugin's MCP process. Treat `sync.failed` as advisory and re-check with `info`/`check` instead of re-running the mutation. Every action returns JSON; a failure is `{"error":{"code","message","next"}}` — follow `next` rather than guessing at a repair.
